## 2. The choice the brief asked to be made explicitly

The brief offered the in-memory comparison and invited a better approach. **The
in-memory comparison is what was built, with one change to make it honest.**

The brief's shape was "run the schema's own SQL against an in-memory database".
To do that, something has to be able to reach the SQL. It was a string literal
inside `init_db()`, so the only ways to reach it were to parse `schema.py` or to
copy it. **Both are the second reader the brief rules out.**

So the literal became a module constant and `init_db()` executes the constant.
**There is now nothing to parse.** `declared_columns()` runs
`conn.executescript(SCHEMA_SQL)` against `:memory:` and reads
`PRAGMA table_info` back; `_live_columns()` reads `PRAGMA table_info` off the
file on disk. Neither side is described anywhere: both are asked of SQLite.

**This is not free and the cost is recorded here.** Moving the literal out of
the call broke `tests/test_vendor_key_naming.py`, which pulled the SQL out of
`init_db()`'s `executescript()` call with `ast.literal_eval`. Five tests went
red. Section 5.3 has the output. The fix is that `_create_statements()` now
returns `schema.SCHEMA_SQL`, which is what that helper existed to obtain, with a
guard asserting `init_db()` still executes that constant. **That is an existing
test file changed by a task that did not ask for it, and it is disclosed here
rather than mentioned in the commit message.**

`PRAGMA table_info` is used in its table-valued form,
`SELECT name FROM pragma_table_info(?)`, so the table name is bound as a parameter
rather than pasted into the statement.

## 3. What refuses, and what does not

| Condition | What happens | Why |
| --- | --- | --- |
| A declared column is not in the live table | **Refuses.** Names every missing column | Something writes it and the write fails |
| A live column the schema does not declare | Starts. Logged at INFO | Nothing writes it and nothing reads it |
| A declared table is not in the live database | Starts, silently | `init_db()` made it a line earlier |
| No database file at all | Starts, silently | First run. `init_db()` makes it, then the check passes |

**The last two are the ones that would have made this check unusable if they
were wrong.** A missing table treated as missing columns would produce a refusal
hundreds of columns long for a fault already fixed one line earlier, and a
missing file treated the same way would mean the pipeline could never start on a
clean machine. Both have a test and both have a mutation.

### The message

This is what Paul would have read at 12:24 on 2026-09-14, generated by running
the real `schema_drift_message()` against a database built from `SCHEMA_SQL`
with the `line_items` line removed:

```
the database at C:\Intellibills\db\receipts.db is missing columns the pipeline
writes: extractions.line_items. Anything that writes one of those fails, so the
pipeline has not started. Send this line on and the columns will be added.
Nothing is lost in the meantime: a receipt stays in the mailbox until a run
files it, and a file stays in the Receipt Inbox until a run moves it.
```

**It is one line, 379 characters, wrapped here and not in the file.** A newline
would reach `run.log` and the console window as one timestamped line followed by
an orphan, because the log format prefixes the first line and no other. There is
a test for it.

**It says to send the line on rather than what SQL to run.** Adding a column to
the live database is a decision, and what the existing rows should hold in it is
not something a start-up check can answer.

**The last sentence was checked rather than written to sound reassuring.**
`fetch_new_messages()` searches `ALL` on every poll and `move_email_to_folder()`
runs only after processing, so an unprocessed email stays in the inbox; a file in
the Receipt Inbox is moved to Processed by the run that handles it. An earlier
draft said "still in the mailbox", which was true of email and silent about the
inbox folder.

### Where it sits in `main()`

`attach_run_log_handler()` → `check_git_status_on_startup()` → **`init_db()` →
the check** → `acquire_lock()` → the poll loop.

Before the lock deliberately: a database the pipeline cannot write is a more
fundamental refusal than a second instance, and refusing first means no lock
file is written and released for a start that was never going to happen.

The two calls are inline in `main()` rather than behind a helper, so the
ordering the brief specifies is readable at the entry point and can be asserted
against `app.py`'s syntax tree.

## 5. Three things that went wrong, disclosed

### 5.1 The `filed_path` anchor matched twice, and the guard caught it

The second missing column in the multi-column tests was written as the one-line
anchor `            filed_path          TEXT,`. **`SCHEMA_SQL` declares that line
byte-identically on `receipts` and on `statements`**, so the uniqueness check in
`without_column()` refused before anything was built:

```
AssertionError: the column line '            filed_path          TEXT,\n' appears 2 times
in SCHEMA_SQL and must appear once.
```

This is `CLAUDE.md`'s substring trap in a new place. The recorded cause is
indentation, a shorter line sitting inside a longer one; here the cause is two
tables declaring the same column with the same formatting.

**It made the tests better rather than merely being fixed.** The anchors now
carry the line above, which differs between the two tables
(`file_hash TEXT NOT NULL` on `receipts`, `file_path TEXT NOT NULL` on
`statements`), and a test was added that removes `filed_path` from each table in
turn and asserts the other stays silent. **A check keyed on column names rather
than on `(table, column)` would pass every other test in the file and fail that
one.** Mutation 3 measures it.

### 10.1 `resolve_receipt.py` writes an extraction and has no check

**Enumerated by walking the syntax tree of all 57 production files at the root
and under `worker\`, which is the rule for a call graph on this project.** `save_extraction()` has **nine call sites across
three files**: `app.py` at 1313, 1404, 1669, 1904 and 2110,
`worker/extraction_pipeline.py` at 321, and `worker/resolution/service.py` at
1174, 1212 and 2271. That is the same nine amendment 466 counted, arrived at
independently.

The three in the resolution service sit inside `_apply_filed_note()` and
`resolve_receipt()`. `app.py` reaches the first through
`_consume_resolution_notes()`, which is the path that raised on 2026-09-14.
**`resolve_receipt.py` calls `resolve_receipt()` directly**, so the CLI reaches
the same INSERT and would meet the same fault as a traceback rather than a
refusal. `discard_receipt.py` reaches neither.

**Nine entry points define `main()` and construct `Repository()`**: `app.py`,
`check_missing_categorisation.py`, `discard_receipt.py`, `import_vendor_csv.py`,
`probe_extract.py`, `probe_layer5.py`, `resolve_receipt.py`,
`retroactive_categorise.py` and `seed_client_vendors.py`. Only `app.py` has the
check, because the brief scopes it to the pipeline's start-up.

**The obvious fix, and it is small**: the same three lines in
`resolve_receipt.py`'s `main()`, returning a non-zero exit code instead of
`return`. One sentence to state, one test to check. **It is a flag rather than
something done in this task because it changes a CLI's exit behaviour**, which is
a decision about a tool Paul runs by hand, and the brief named `main()` and the
first poll.

### 10.2 The refusal is unreachable without a second entry point

**This is a consequence worth stating once, and nothing here is broken.** `main()` is the only place
that refuses, and `main()` is what `IntelliBooks.bat` starts. **Anything that
imports `Repository` and never goes through `main()` gets the old behaviour**, a
traceback from SQLite at the first write. That is eight of the nine above and the
console when it is built. **The obvious fix is 10.1 generalised**: the check
called from each entry point's `main()`. Whether that is worth eight copies of
three lines, or a shared `worker/logging_setup.py`-shaped helper each entry point
calls, is a design decision and is Paul's.

### 10.3 `init_db()` is now called twice on a normal start

`main()` calls it, and `Repository.__init__` calls it again on the first poll.
**Harmless and measured**: it is eleven `CREATE TABLE IF NOT EXISTS` statements
and six `CREATE INDEX IF NOT EXISTS`, counted off `SCHEMA_SQL` rather than
estimated, all no-ops the second time. ~~nine `CREATE INDEX`~~ **Corrected

**No fix proposed**: removing the call from `Repository` would change behaviour
